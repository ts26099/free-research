1 장한 장 요약

이 프로그램이 하는 일

축구 경기 영상을 넣으면, 프레임마다 선수·골키퍼·심판·공이 화면 어디에 있는지를 찾아 CSV 한 장으로 뽑아 준다. 그게 전부다. 명령어를 칠 필요가 없도록 설치·실행·확인 도구가 함께 들어 있다.

기여도는 어디서 계산되나

핵심 16개 파일 안에는 기여도를 계산하는 코드가 없다. 전부 '측정' 단계다. 기여도(SC · PR · PA · DPI · TC)는 별도 파일 soccer_dpi_pa_v7.py 가 계산한다. 두 프로그램은 서로를 전혀 모르고, tracks.csv 파일 하나로만 이어진다. 그 이음매가 지금 어긋나 있어서(11장), 현재 상태로는 tracks.csv 를 기여도 코드에 그냥 넣을 수 없다.

지금 상태를 세 줄로

항목상태내용
검출·추적 품질좋음 축구 전용 모델 + 공 전용 모델 + 6단계 공 오검출 필터. 페널티 마크·축구화·골대 기둥까지 실측으로 잡아내는 수준이다. 이 부분은 상용 도구에 견줄 만하다.
추적 ID 지속문제 지금 설정(vid_stride 3 · imgsz 640)에서는 한 선수가 수십 개의 번호를 갈아탄다. 코드 주석의 실측값으로 트랙 지속 중앙값이 0.2~0.5초다. '선수별' 기여도 표가 무의미해지는 직접 원인.
좌표 단위문제 CSV 좌표는 화면 픽셀이다. 미터로 바꾸는 호모그래피가 어디에도 구현되어 있지 않다. 기여도 수식의 상수가 전부 미터 기준이라, 이 상태로는 계산이 성립하지 않는다.

즉 측정 장비는 잘 만들어져 있는데, 눈금이 안 매겨져 있고 피사체에 이름표가 안 붙어 있는 상태다. 13장이 그 두 가지를 순서대로 고치는 방법이다.

3 장실행 계층 — 더블클릭에서 분석까지

이 계층의 파일들은 분석 품질과 직접 관계가 없어 보이지만, 실제로는 두 가지를 결정한다 — GPU 를 쓸 수 있는가, 그리고 추적 ID 가 제대로 붙는가. 둘 다 결과를 크게 바꾼다.

3.1 SoccerTracker.exe / SoccerTracker.cs — 검은 창 없이 띄우기

C# 129행짜리 실행기다. 윈도우에 기본으로 들어 있는 컴파일러(csc.exe)로 빌드하므로 빌드 도구를 따로 설치할 필요가 없다. 하는 일은 파이썬을 찾아 app.py 를 띄우는 것뿐이다.

순서찾는 것이유
①venv\Scripts\pythonw.exe 이 폴더 전용 가상환경. pythonw(w 가 붙은 것)를 쓰면 검은 콘솔 창이 안 뜬다.
②시스템 파이썬 중 ultralytics·torch 가 있는 것 이미 깔려 있으면 설치를 기다릴 이유가 없다. 확인은 importlib.util.find_spec 으로 한다 — 실제로 import 하지 않아서 빠르다(torch import 는 몇 초 걸린다).
③START.bat 아무것도 없으면 설치부터 해야 하고, 그건 진행 상황이 보여야 하므로 콘솔이 뜨는 배치로 넘긴다.

이 파일 위에 영상을 끌어다 놓으면 그 경로가 그대로 app.py 의 인자로 전달된다. 탐색 과정에는 30초 타임아웃이 걸려 있어, 응답 없는 파이썬 하나 때문에 프로그램이 멈추지 않는다.

3.2 START.bat — 같은 판단을 배치로

exe 없이도 똑같이 동작하도록 만든 대안 경로다. 순서는 exe 와 같고, 세 번째 단계에서 PowerShell 스크립트를 부른다.

powershell -NoProfile -ExecutionPolicy Bypass -File "ensure_python.ps1"
set "PYEXE="
if exist "_python_path.txt" set /p PYEXE=<"_python_path.txt"
del "_python_path.txt"
"%PYEXE%" "bootstrap.py" %*

PowerShell 이 찾아낸 파이썬 경로를 임시 텍스트 파일로 주고받는다. 배치와 PowerShell 사이에 값을 넘기는 가장 확실한 방법이고, 쓰고 나서 바로 지운다.

3.3 ensure_python.ps1 — 파이썬이 아예 없을 때

121행이지만 함정을 세 개나 피해 간다.

(1) Microsoft Store 껍데기 걸러내기

if ($Exe -like "*\WindowsApps\*") { return $false }

윈도우 10/11 에는 python.exe 라는 이름의 0바이트 껍데기가 기본으로 들어 있다. 실행하면 Microsoft Store 가 열릴 뿐이다. 이걸 파이썬으로 착각하면 설치가 무한히 실패한다.

(2) 진짜 파이썬인지 확인하는 방법

$ver = & $Exe -c "import sys,tkinter;print(sys.version_info[0]*100+sys.version_info[1])"
return ([int]$ver -ge 309)   # 3.9 이상 + tkinter 존재

버전만 보지 않고 tkinter 를 함께 import 해 본다. GUI 가 필요하기 때문이다. tkinter 없이 설치된 파이썬은 나중에 창을 못 띄운다.

(3) 관리자 권한 없이 설치

/quiet InstallAllUsers=0 PrependPath=1 Include_tcltk=1 Include_pip=1

사용자 영역에 조용히 설치한다. 3.13 이 아니라 3.12 를 쓰는데, 최신 버전은 일부 패키지의 빌드된 휠이 아직 없을 수 있어서다. 직접 내려받기가 막힌 환경을 위해 winget 으로 한 번 더 시도한다.

3.4 bootstrap.py — 설치 순서가 데이터 품질을 결정한다

평범한 설치 스크립트처럼 보이지만, 여기 적힌 순서가 나중의 CSV 품질을 직접 결정한다.

순서 ① torch 를 ultralytics보다 먼저

gpu = has_nvidia_gpu()                 # nvidia-smi 가 도는지로 판단
if gpu:  pip install torch torchvision --index-url .../whl/cu124
else:    pip install torch torchvision
pip install ultralytics                # ← 반드시 torch 다음

ultralytics 를 먼저 깔면 의존성 해결 과정에서 CPU 전용 torch 휠을 끌어온다. GPU 가 있는 PC 인데도 CPU 로 돌아 45분 영상이 몇 분 → 몇 시간이 된다.

순서 ② lap 을 미리

이것을 빠뜨리면 CSV 가 통째로 못 쓰게 된다 lap 은 ByteTrack 의 헝가리안 매칭 라이브러리다. 없으면 ultralytics 가 첫 추적 도중에 알아서 설치하는데, 그 회차는 track_id 가 전부 -1 로 나온다.

track_id 가 -1 이면 "같은 선수"라는 개념이 사라진다. 프레임별 좌표는 있지만 누가 누구인지 모르므로 기여도 계산의 선수별 집계가 원천적으로 불가능하다. 몇 시간을 돌리고도 버려야 하는 CSV 가 나온다. requirements.txt 에도 같은 경고가 주석으로 달려 있다.

순서 ③ 실패해도 되는 것과 아닌 것

5 장tracker.py (1) — 분석을 시작하기 전에

2,593행짜리 이 파일의 구조는 의외로 단순하다.

준비(5장)  →  프레임 루프(6장)  →  후처리(7장)  →  저장 어려운 것은 그 사이에 낀 필터들인데, 필터 하나하나가 "무엇을 잘못 잡았는가"라는 구체적 관찰에서 출발한다. 코드 주석에 그 관찰과 실측 수치가 거의 다 적혀 있다.

5.1 Config — 80개 설정값

@dataclass 하나에 모든 기준값이 들어 있고 config.json 으로 저장·복원된다. 읽을 때 기본값의 타입에 맞춰 변환하고, 안 맞으면 그 항목만 기본값을 지킨다.

current = getattr(cfg, key)
if isinstance(current, bool):  value = bool(value)
elif isinstance(current, int): value = int(value)
...
except (TypeError, ValueError): continue     # 이 항목만 기본값 유지

손으로 잘못 고친 config.json 하나 때문에 분석 한참 뒤 엉뚱한 지점에서 터지는 것을 막는 장치다. 모르는 키는 그냥 무시하므로, 옛 설정 파일도 그대로 읽힌다.

5.2 모델 준비 — GPU 가 없으면 OpenVINO 로 바꿔 둔다

if not cfg.use_openvino or has_cuda():
    return YOLO(cfg.model)          # GPU 가 있으면 원본 .pt 가 더 빠르다
...
cache = root / "models" / f"{stem}_{cfg.imgsz}_openvino_model"
if not (cache / "metadata.yaml").exists():
    exported = YOLO(cfg.model).export(format="openvino", imgsz=cfg.imgsz)

CPU 추론이 1.5~2배 빨라진다(30분 영상 기준 20.3분 → 12.8분). 변환본은 해상도마다 다르므로 해상도를 파일명에 붙여 캐시한다. 변환에 실패해도 원본으로 되돌아가 계속 진행한다.

지금 설정에서는 이 가속이 꺼져 있다 config.json 의 use_openvino 가 false 다. GPU 가 없는 PC 라면 이것만 켜도 분석 시간이 3분의 2로 줄어든다. 처음 한 번 1~3분의 변환 시간이 든다.

5.3 트래커 설정 자동 생성 — 두 가지를 바로잡는다 중요

resolve_tracker() 는 ultralytics 의 기본 bytetrack.yaml 을 읽어 값을 고친 사본을 만들어 쓴다. 고치는 것은 두 가지다.

(1) 신뢰도 임계값을 conf 에 맞춘다

settings["track_high_thresh"] = cfg.conf          # 0.10
settings["new_track_thresh"]  = cfg.conf          # 0.10  (기본 0.25)
settings["track_low_thresh"]  = max(0.01, cfg.conf * 0.5)

ByteTrack 은 new_track_thresh(기본 0.25) 미만인 검출로는 새 트랙을 시작하지 않는다. 사용자가 conf=0.1 로 낮춰 약한 검출까지 받기로 했는데 트래커 임계값이 0.25 로 남아 있으면, 그 검출들은 표에 잡히되 track_id 가 -1 로 찍힌다. 이 기능이 그것을 막는다.

(2) track_buffer 를 stride 로 나눈다

stride = max(1, int(cfg.vid_stride))                      # 3
buffer_frames = max(5, round(int(cfg.track_buffer) / stride))   # 30 / 3 = 10
settings["track_buffer"] = buffer_frames
1판 정정 ① 1판에서 저는 "track_buffer 30 은 원본 프레임 기준이라 stride 3 이면 실질 10프레임뿐"이라고 썼는데, 이는 코드를 잘못 읽은 것이다. 사실은 그 반대다 — 코드가 일부러 stride 로 나눠서 원본 프레임 기준의 의미를 유지한다. 트래커는 3장마다 한 장만 보므로, 30 을 그대로 두면 원본 기준 90프레임(3.6초)을 기억하는 셈이 되어 그 사이 다른 선수가 그 자리에 들어와 ID 를 물려받기 딱 좋다. 나눠서 10으로 두면 원본 기준 30프레임(약 1.2초)이 된다.

결론은 바뀌지 않는다 — 1.2초는 여전히 짧으므로 track_buffer 를 올리는 것은 유효한 개선이다(13장). 다만 "버그라서 올려야 한다"가 아니라 "의도된 값이 이 영상에는 짧다"가 맞다.

5.4 팀 색 보정 — 유니폼 색으로 두 팀 가르기

심판은 경기장 안에서 뛰므로 위치로는 못 거른다. 그래서 색을 쓴다. 분석 시작 전에 한 번만 한다.

단계함수내용
①torso_color() 상자에서 위 15~50% · 가운데 절반만 잘라낸다(머리와 다리를 뺀다). 잔디 초록 픽셀을 뺀 뒤 남은 픽셀의 Lab 색공간 a·b 두 채널 중앙값을 그 사람의 색으로 삼는다. 밝기(L)를 버리는 것이 핵심 — 그늘의 선수와 햇빛 아래 선수를 같은 색으로 묶기 위해서다.
②calibrate_teams() 영상 전체에서 균등 간격으로 16장만 뽑아 상체 색을 모은다. 이때 잔디 밖 사람은 빼고, '선수' 클래스에서만 뽑는다(심판·골키퍼 유니폼이 섞이면 군집이 흐려진다). 12명 미만이면 팀 구분을 포기한다.
③_kmeans() 직접 구현한 작은 k-means(sklearn 의존을 피하려고). 4덩어리를 만들고 가장 큰 두 덩어리를 양 팀으로 본다. 초기 중심은 k-means++ 비슷하게 서로 먼 점부터 고른다.
④군집 병합 같은 팀이 그늘·조명 때문에 두 군집으로 쪼개지는 일이 잦다. 남은 군집이 어느 팀 색에 "두 팀 사이 거리의 0.5배"보다 가까우면 그 팀으로 합친다. 어디에도 안 붙으면 -1.
초록 유니폼 문제 — 필터가 상체를 통째로 지우는 경우 ①의 "잔디 초록을 뺀다"는 단계가 유니폼이 초록 계열일 때 상체를 전부 지워 버린다. 실측 — 브라질(노랑) 대 멕시코(초록) 영상에서 상체 36개를 재니 36개 전부가 잔디로 판정됐다. 초록 유니폼은 당연하고, 노란 유니폼도 색조가 34 라 잔디 범위(30~95) 하한 안쪽에 들어갔다. 팀 보정 표본이 342명 중 41명으로 줄고 96%가 미분류됐다.

그래서 torso_grass_fallback 이 있다 — 남는 픽셀이 12개 미만이면 지우지 말고 패치 전체를 쓴다. 상체 패치는 원래 대부분이 유니폼이라 잔디가 조금 섞여도 중앙값이 버틴다. 같은 영상에서 표본이 41 → 342명으로 돌아왔고 두 군집이 거리 40.2 로 잘 갈렸다.
team_imgsz — 16장만 크게 보는 트릭 검출과 팀 구분은 요구가 다르다. 축구 모델은 640 에서도 선수를 거의 다 찾지만(22.7명 vs 1280의 23.0명), 팀 색은 상체 픽셀이 있어야 뽑힌다. 640 에서는 상체가 20px 남짓이라 실측상 41%가 team=-1 로 샜다.
팀 색 보정은 영상 전체에서 16장만 보므로, 그 16장만 높은 해상도로 처리하면 전체 비용은 거의 안 늘면서 팀 구분만 좋아진다. 지금 설정은 team_imgsz: 960 (검출은 640) — 잘 잡혀 있다.

5.5 구간 분석과 워밍업

python tracker.py "경기.mp4" --from 12:00 --to 15:00
→ results/경기 12m00s-15m00s/ 에 따로 저장 (프레임 번호는 원본 기준)

90분 경기 전체는 CPU 로 몇 시간이 걸리므로 구간 분석이 현실적이다. 구간을 잘못 넣는 실수가 흔해서 네 가지를 미리 검사한다 — 음수 시각, 끝이 시작보다 앞, 시작이 영상 길이를 넘음, 끝이 영상 길이를 넘음(이건 잘라서 진행). 조용히 빈 결과를 만들지 않고 이유를 알려 준다.

워밍업(range_warmup_sec: 4.0): 구간 시작보다 4초 앞에서부터 추적기를 미리 돌리되 기록은 하지 않는다. ByteTrack 은 갓 시작하면 트랙이 확정되지 않아 처음 1.5초쯤이 흔들리기 때문이다. 워밍업을 거치면 그 뒤로는 전체 분석과 93% 일치한다고 주석에 적혀 있다.

6.2 사람 필터 — 경기장 밖과 화면에 박힌 그래픽

잔디 마스크 (pitch_mask)

프레임을 1/4 로 줄여서 계산한다(충분하고 훨씬 빠르다). 순서는 이렇다.

  1. HSV 색상 30~95 · 채도 30 이상을 초록으로 골라낸다
  2. 모폴로지 연산으로 잔구멍을 메우고 자잘한 초록 노이즈를 지운다
  3. 초록이 화면의 15% 미만이면 포기하고 None 을 돌려준다(실내·리플레이 화면)
  4. 연결 요소 중 가장 큰 덩어리만 남긴다
  5. _fill_holes() — 테두리를 덧대고 바깥에서 물을 채운 뒤 뒤집어 안쪽 구멍만 메운다. 선수가 잔디를 가려 생긴 구멍은 채워지고 터치라인 바깥은 바깥으로 남는다
  6. 가장자리를 16px 안쪽으로 좁힌다(pitch_shrink)

그리고 사람 상자의 발밑 점이 마스크 밖이면 버린다. 중심점이 아니라 발밑인 이유는 사람이 땅을 딛고 서 있기 때문이다. 공에는 적용하지 않는다 — 높이 뜬 공은 관중석을 배경으로 걸친다.

축구 모델에서도 이 필터를 켜 두는 이유 — 실측으로 뒤집힌 판단 처음에는 "축구 모델은 스태프·관중을 안 잡는다"며 껐는데 틀렸다. 전술 영상 10:00~13:00 구간에서 2초마다 91장을 뽑아, 잔디 밖으로 판정된 사람 51건을 전부 눈으로 확인한 결과:
  · '선수' 라벨 44건 — 파란 트랙 위 스태프, 노란 조끼 안전요원, 사진기자, 코치
  · '심판' 라벨 7건 — 펜스 옆 안전요원 4, 광고판 글자 3
진짜 선수는 0건이었다. 선수는 스로인·코너킥 때도 흰 선 밖 잔디 여백 위에 서므로 '초록 잔디 위' 기준으로는 빠지지 않는다.

실패해도 해가 없는 쪽으로 실패한다 — 관중 색이 잔디와 겹치면 마스크가 화면 전체를 잔디로 봐서 아무것도 안 거른다.

중계 그래픽 필터 (static_tracks) — 축구 모델에서는 꺼진다

static_on = cfg.drop_static_tracks and not profile.is_soccer
1판 정정 ② 1판에서는 이 필터가 항상 동작하는 것처럼 설명했는데, 축구 전용 모델을 쓰면 자동으로 꺼진다. config.json 에 drop_static_tracks: true 라고 적혀 있어도 그렇다. 이유는 두 가지다 — 축구 모델은 중계 그래픽 속 인물을 애초에 잘 안 잡고, 붙박이 판정이 골키퍼처럼 한자리에 오래 서 있는 사람을 지울 수 있기 때문이다. 로그에도 "중계그래픽 필터는 이 모델에 불필요하므로 끕니다"라고 찍힌다.

판정 규칙 자체는 이렇다(COCO 모델을 쓸 때만 적용).

(이동 폭 ÷ 평균 키) < 0.10  그리고  등장 ≥ 15프레임  →  사람이 아니라 그래픽 이동 폭을 키로 나누는 이유: 멀리 있어 작게 잡힌 선수도 같은 자로 재기 위해서다. 픽셀 거리를 그대로 쓰면 먼 곳의 진짜 선수가 '안 움직인 것'으로 걸린다.

6.4 공 파이프라인 — 여섯 단계

이 프로그램에서 가장 공들인 부분이다. 이유는 분명하다. 공 위치가 틀리면 기여도가 통째로 틀린다. 공이 어디 있느냐로 "누가 소유자인가", "어느 팀이 공격 중인가", "위험한 공간이 어디인가"가 전부 결정된다.

왜 이렇게까지 하는가 — 실측 오검출 리버풀-레알 경기 50초 구간을 눈으로 전수 판정한 결과, 공 검출 587건 중 281건(48%)이 페널티 마크였다. 게다가 마크가 잡히는 프레임에서는 진짜 공을 대신 놓치는 일이 많았다. 무작위 104건 판정에서는 흰 축구화가 19건(18%)으로 가장 큰 오류였다.

① 공 전용 모델

선수 모델은 공을 잘 못 찾는다. 공은 지름 12px 남짓이라 선수와 함께 학습된 모델에서는 늘 뒷전이다. 같은 60프레임 실측 — 선수 모델 @1280 은 42장에서 발견하고 968ms/장, 공 전용 모델 @1280 은 50장에서 발견하고 134ms/장. 더 잘 찾으면서 7배 빠르다. 공 전용 모델을 쓰면 주 모델의 공 검출은 통째로 버린다(같은 공을 두 줄로 적지 않기 위해).

해상도는 ball_imgsz: 1920(원본 해상도)이다. 1280 → 1920 으로 올리자 먼 쪽 터치라인의 공(7px 남짓)을 0.07 → 0.83 신뢰도로 봤고, 공이 잡히는 프레임이 57.0% → 68.9% 가 됐다. 비용은 공 모델 140 → 330ms/장.

7 장tracker.py (3) — 분석이 끝난 뒤의 후처리

프레임 하나만 봐서는 판단할 수 없는 것들이 있다. "이 트랙은 전체적으로 어느 팀인가", "이 트랙은 처음부터 끝까지 안 움직였나", "이 약한 공 후보가 확실한 공과 이어지나". 전부 궤적 전체를 봐야 알 수 있으므로 CSV 를 다 쓴 뒤에 한 번 더 훑는다.

후처리 순서 — 이 순서가 중요하다

① finalize_tracks() : 팀 다수결 + 골키퍼 트랙 확정 + 붙박이 사람/공 제거 + 심판 제외
② chain_ball() : 공 궤적 잇기 (확실한 공에서 앞뒤로 약한 후보를 따라간다)
③ interpolate_ball() : 남은 짧은 공백을 직선으로 메움
④ summary.json 저장  →  ⑤ 결과 영상 만들기 ②가 ③보다 먼저인 이유: 잇기로 실제 관측을 먼저 채워 넣어야, 보간이 메울 공백이 줄고 보간 구간도 짧아진다. ④가 ⑤보다 먼저인 이유는 7.6 참고.

7.1 팀 다수결 (finalize_tracks)

final = {tid: _decide_team(votes) for tid, votes in team_votes.items()}

def _decide_team(votes):
    return min(votes.items(), key=lambda kv: (-kv[1], kv[0] < 0, kv[0]))[0]

표가 가장 많은 팀으로 정하되, 동률이면 실제 팀(0/1)을 -1 보다 우선한다. 멀어서 상체가 안 잡힌 프레임이 -1 로 세어지기 때문에, 동률에서 -1 을 고르면 손해다.

drop_non_team(심판 제외)도 이 단계에서 처리한다. 프레임 단위로 미리 버리면 다수결에서 이겼을 선수가 중간중간 사라지므로, 확정된 뒤에 버려야 맞다.

작업은 CSV 를 한 줄씩 흘려 읽어 임시 파일에 쓴 뒤 갈아끼우는 방식이다. 도중에 실패하면 원본을 그대로 남기고 None 을 돌려준다 — 몇 시간짜리 분석 결과를 날릴 수는 없다.

7.2 골키퍼 트랙 확정 — 모델이 골대 기둥을 골키퍼라고 부른다

가장 흥미로운 필터다. 실측이 이렇다.

  • 진짜 골키퍼 트랙은 골키퍼 라벨이 3~39%뿐이고 나머지 프레임은 '선수' 라벨이었다.
  • 반대로 골대(세로 기둥·그물)는 골키퍼 라벨이 69~100%였다. 학습 데이터에서 골키퍼가 늘 골대 옆에 서 있어서 모델이 "기둥 = 골키퍼"로 배운 것이다.

영상에서는 이것이 "번호가 떴다 사라졌다 바뀌는" 현상으로 보였다 — 골키퍼일 때만 GK 로, 나머지는 번호 박스로 찍혔기 때문이다. 그래서 트랙 단위로 가른다.

조건판정처리
유니폼 색이 팀 0 또는 1필드 선수골대 근처에서 잠깐 잘못 찍힌 것. 골키퍼 라벨을 선수로 되돌린다.
팀 -1 이고 트랙 전체 신뢰도 중앙값 < 0.50골대선수 라벨 행까지 트랙을 통째로 뺀다.
그 외골키퍼트랙 전체를 골키퍼로 통일한다.

임계값 0.50 의 근거: 트랙 전체 신뢰도 중앙값이 골대는 0.22·0.30·0.34·0.34·0.36·0.41, 골키퍼는 0.60·0.65·0.75·0.77·0.80·0.80·0.81 이었다. 골키퍼 라벨이 붙은 행만 보면 0.41 / 0.45 로 거의 붙어 있는데, 진짜 골키퍼는 선수로 찍힌 행의 신뢰도가 높아 트랙 전체로 보면 0.41 / 0.60 으로 벌어진다. 신뢰도는 20칸 히스토그램으로 모아 두었다가 중앙값을 낸다.

7.3 붙박이 공 제거 (static_ball_tracks)

공은 경기장에서 가장 많이 움직이는 물체다. 프리킥으로 멈춰 서 있어도 결국 차이므로 트랙 전체로 보면 반드시 움직인다. 실측에서 흰 옷 입은 선수의 몸통이 12프레임 연속(움직임 1px) 공으로 잡혔는데, 그런 것을 뺀다.

(이동 폭 ÷ 평균 공 크기) < 1.0  그리고  등장 ≥ 5프레임  →  공이 아니다

7.4 궤적 잇기 (chain_ball) — 시간축으로 진짜 공을 가려낸다

한 프레임만 보면 달리는 선수의 흰 축구화는 공과 구별되지 않는다 — 밝기 222~250, 채움 0.62~0.83, 크기비 0.20~0.27 로 전부 공의 범위 안에 있다. 차이는 시간축에 있다. 진짜 공의 약한 후보들은 서로 이어져 확실한 공으로 연결되지만, 축구화는 어떤 확실한 공과도 이어지지 않는다.

끝점(anchor) 고르기 — 세 조건을 다 만족해야 한다

  1. 그 프레임에 뽑힌 공의 신뢰도가 0.60 이상
  2. 전체 화면에서도 같은 자리(6px 안)를 0.60 이상으로 봤을 것 — 확대 창은 축구화도 0.7 로 부풀리므로, 확대 창 신뢰도로 끝점을 잡으면 축구화 궤적이 끝점이 되어 버린다
  3. 앞뒤 1~2 처리프레임에 40~80px 안으로 이어지는 공이 있을 것

끝점에서 앞뒤로 따라가기

tol = 28.0 + 0.6 × |속도| × (놓친횟수+1)        # 빠를수록 넉넉하게
후보 선택 = min(거리 − 20 × 신뢰도)              # 가깝고 확신 있는 것
속도 갱신 = 0.5 × 이전속도 + 0.5 × 실제이동      # 급변을 눌러 준다
연속 2회까지는 후보가 없어도 예측 위치로 계속 간다

이렇게 이어진 길이가 3 이상이고 기존 선택과 30px 이상 떨어져 있을 때만 바꾼다. 실측(전술 10:00~13:00) 오프라인 재현에서 교체 84건 · 추가 161건이었고, 교체 78건을 눈으로 비교하니 좋아진 것 약 50, 나빠진 것 약 5(점선 조각·손), 불분명 약 20 이었다. 추가 64건 중 틀린 것은 약 4건.

허용 오차 28px 의 근거: 14px 는 속도를 모를 때 너무 좁아 이어지지 않았고, 28px 에서 문제 구간(10:06, 공이 뜬 순간 놓치자 확대 창이 날아가던 방향의 축구화를 0.3~0.7 로 잡았던 구간)이 전부 바로잡혔다.

7.5 짧은 공백 메우기 (interpolate_ball)

양 끝이 엄격한 끝점이고, 공백이 0.4초 이하이고, 두 끝점 사이 속도가 초당 선수 키 20배 이하일 때만 직선으로 메운다. 메운 행은 interpolated=1, conf=0 으로 표시한다.

0.4초라는 상한이 나온 과정 — 처음엔 2.0초로 넣었다가 틀렸다 측정된 공을 일부러 지우고 양옆 끝점으로 보간해 실제 위치와 비교했다(단위: 선수 키).
빈 구간오차 중앙값키의 1/3 이내 비율
0.16초0.01100%
0.6초0.1876%
0.8초0.2858%
1.6초0.9117%
2.0초로 메운 점 52개를 눈으로 보니 제대로 맞은 것이 29%뿐이었다. 공은 짧은 시간에도 방향을 바꾸고(드리블·패스) 카메라가 패닝해서 픽셀상 경로가 직선이 아니다. 상한별 이득은 0.3초 +3%p / 0.4초 +4%p / 0.5초 +5%p 인데, 0.4초면 오차 90% 지점에서도 선수 키의 8%(약 5px)라 공 위에 떨어진다.
롱패스처럼 몇 초짜리 공백은 이 방법으로 메울 수 없다. 선을 그으면 틀린다.

7.6 저장 순서 — 몇 시간짜리 분석을 지키는 설계

1. tracks.csv 완성
2. 후처리 (팀·골키퍼·붙박이·잇기·보간)
3. summary.json 저장          ← 여기서 '이 영상은 끝났다'가 확정된다
4. 결과 영상 만들기 (수십 분)
5. 영상이 성공하면 summary.json 을 한 번 더 갱신 (result_video, elapsed_sec)

3과 4의 순서가 핵심이다. 긴 경기 영상은 인코딩에만 수십 분이 걸리는데, 그 도중에 끊겨서 summary.json 이 없으면 '이미 한 건 건너뛰기'가 안 먹어 몇 시간짜리 분석을 처음부터 다시 돌게 된다. 이 순서면 영상이 실패하거나 중단돼도 분석 결과는 남는다. (그래도 사고가 나면 recover_summary.py 가 CSV 에서 되살린다.)

한 장도 못 읽었으면 CSV 와 폴더를 지우고 None 을 돌려준다 — summary.json 을 안 써야 다음에 재시도되기 때문이다.

7.7 결과 영상은 왜 draw_boxes.py 를 부르나

ultralytics 의 save=True 를 안 쓰는 이유가 있다. 그쪽은 처리한 프레임만 원본 fps 로 이어붙이기 때문에, vid_stride 를 쓰면 3배속으로 뚝뚝 끊기는 영상이 나온다. draw_boxes.py 는 원본을 처음부터 다시 훑으면서 분석 안 한 프레임에는 직전 박스를 남겨두므로 길이도 속도도 원본과 같고, 팀 색까지 반영된다.

구간 분석이면 영상도 그 구간만 그린다. 예전에는 구간을 안 넘겨서 5초만 분석해도 90분 경기 전체를 인코딩했다(10분 만에 548MB).

8.3 이 설정의 약점 세 가지

  1. vid_stride 3 + imgsz 640 — 둘이 겹쳐 최악의 조합이다. 박스가 작은데(640) 시간 간격까지 넓어서(0.125초) 박스 겹침이 0 이 되기 쉽다. 둘 중 하나만 바꿔도 크게 개선된다.
  2. OpenVINO 꺼짐 — GPU 가 없다면 아무 손해 없이 시간을 1/3 줄일 수 있다. stride 를 3 → 2 로 올리면서 OpenVINO 를 켜면 총 시간은 거의 그대로 두고 추적 품질만 올릴 수 있다.
  3. 심판이 CSV 에 남음 — 기여도 단계에서 반드시 걸러야 한다. 다만 축구 모델은 골키퍼도 -1 로 표시할 수 있으므로, class_name 으로 골키퍼는 남기고 referee 만 빼야 한다. 설정에서 drop_non_team: true 로 바꾸면 골키퍼까지 사라질 수 있어 위험하다.

8.4 1판에서 잘못 쓴 것 두 가지 (정정)

정정 ① · track_buffer 1판: "기본 30은 원본 프레임 기준이라 stride 3이면 실질 10프레임뿐이다"(버그처럼 서술)
사실: resolve_tracker() 가 일부러 stride 로 나눠 원본 기준 의미를 보존한다. 나누지 않으면 오히려 3.6초를 기억해 다른 선수에게 ID 가 넘어간다.
영향: 권고 자체(값을 올려 보라)는 유효하지만, 이유가 다르다.
정정 ② · 중계 그래픽 필터 1판: 이 필터가 항상 동작하는 것으로 설명
사실: static_on = drop_static_tracks and not is_soccer — 축구 모델에서는 자동으로 꺼진다. 붙박이 판정이 골키퍼처럼 한자리에 오래 서 있는 사람을 지울 위험 때문이다.
영향: 지금 설정에서는 이 필터를 신경 쓸 필요가 없다.

10.1 무엇을 재려는 것인가

골·어시스트·패스 성공률은 공에 닿은 사람만 기록한다. 그런데 축구에서 일어나는 일의 대부분은 공 없이 일어난다. 수비수가 공간을 미리 막아 패스 선택지를 지운 것, 미드필더가 소유자에게 붙어 시간을 빼앗은 것, 공격수가 좋은 자리에 서서 수비를 끌고 간 것 — 어떤 기록지에도 안 남는다. 그것을 세 축으로 나눠 잰다.

지표무엇을언제 나오나한 줄 정의
SC공간 통제팀이 수비할 때위험한 공간을 상대보다 먼저 덮고 있었는가
PR압박 기여팀이 수비할 때공 가진 상대에게 얼마나 붙었고 얼마나 빠르게 좁혔는가
PA패스 유인팀이 공격할 때동료가 나에게 패스하고 싶을 만큼 좋은 선택지였는가
DPI수비 합성—0.5·z(SC) + 0.5·z(PR)
TC총 기여—셋을 순위 정규화해 1/3씩 합친 값 (+ 포지션 보정본 TC_adj)
SC·PR 과 PA 는 서로 다른 프레임에서 나온다 우리 팀이 공을 갖고 있는 동안 우리 선수에게는 PA 만 쌓이고 SC·PR 은 쌓이지 않는다. 그래서 양 팀이 공수를 주고받는 구간이 충분해야 세 지표가 다 모인다. 짧은 클립에서 한 팀이 계속 공을 갖고 있었다면 한쪽은 수비 기록이, 다른 쪽은 공격 기록이 아예 없어 TC 를 낼 수 없다.

10.3 공 소유 판정 — 모든 계산의 기준점

  1. 가장 가까운 선수를 찾아 POSS_RADIUS(데이터를 보고 2~8m 중 자동 결정) 이내면 소유자로 인정
  2. 데드볼 제외 — 공이 라인 밖 1m 를 넘으면 소유자를 두지 않는다. 90분 경기에서 공이 실제로 살아 있는 시간은 55~60분뿐이고, 스로인을 기다리며 자리 잡는 배치를 공간 다툼으로 계산하면 안 된다
  3. 공중볼 제외 — 공 높이가 1.5m 를 넘으면 소유자를 두지 않는다. 헤더 경합은 점프와 타이밍으로 결정되므로 지면 2D 거리로는 판정할 수 없다. (단, tracks.csv 에는 높이 열이 없어 현재는 적용되지 않는다)
  4. 전환 인정 — 1.5초보다 짧으면서 앞뒤가 같은 팀인 구간은 잡음으로 보고 흡수한다. A→B→A 의 짧은 B 는 지우고, A→B→C 의 B 는 실제 전환이므로 남긴다
  5. usable 판정 — 소유팀이 정해졌고 양 팀 모두 명목 인원의 80% 이상이 추적된 프레임만 쓴다
usable 이 왜 필요한가 SC 는 경기장 전체 격자를 "가장 가까운 수비수"에게 나눠 주는 계산이다. 뒤쪽 수비수가 화면 밖으로 빠지면 남은 수비수가 그 빈 자리의 공간 점유까지 대신 받아 SC 가 부풀려진다. 한 대의 카메라로 만든 좌표는 경기장의 2/3 정도만 담으므로, usable 비율이 낮게 나오는 것이 오히려 정직한 신호다.

10.4 SC — 공간 통제 (Shapley 배분)

1걸음 · 격자와 위험도

w(칸) = exp( −골대까지거리 ÷ 18 ) × exp( −공까지거리 ÷ 20 ) × 칸넓이 1m 격자이므로 105×68 경기장이면 약 7,140칸. "위험하다"는 것은 내 골대에 가깝고 동시에 공에 가깝다는 뜻이다. 둘 중 하나만 만족하는 칸은 값이 급격히 떨어진다.

예 — 내 골대에서 20m, 공에서 15m 떨어진 칸: exp(−20/18) × exp(−15/20) = 0.329 × 0.472 = 0.156. 골문 바로 앞(골대 5m, 공 5m)이면 0.757 × 0.779 = 0.590 으로 약 네 배다.

2걸음 · 누가 그 칸을 통제하나

그 칸까지의 거리가 가장 가까운 공격수보다 가까운 수비수들이 그 칸을 통제한다고 본다. 한 명일 수도, 세 명일 수도, 아무도 없을 수도 있다(그 칸은 공격팀 영역이므로 아무에게도 안 간다).

3걸음 · 나누기

칸을 함께 덮은 수비수가 k 명이면 각자 w(칸) ÷ k 씩 가져간다 협력게임 이론의 Shapley 값에서 효율성과 대칭성을 만족하는 배분이다.
· 효율성: 한 프레임에서 모든 수비수가 받은 SC 의 합 = 통제된 총 위험도 (코드가 매번 검산한다)
· 대칭성: 같은 칸을 같은 조건으로 덮은 두 수비수는 같은 값을 받는다
덕분에 "혼자 넓게 막은 수비수"와 "둘이 겹쳐 막은 수비수"가 공평하게 평가된다.

프레임마다 위험도 총량이 크게 다르므로(공이 자기 박스 안이면 총량 320, 상대 박스 쪽이면 29 로 11배 차이) 원값 SC 와 함께 팀 총량 대비 몫인 SC_share 도 낸다. 효율성 공리 덕분에 한 프레임의 share 합은 정확히 1 이다.

10.5 PR — 압박 기여

목표물은 상황에 따라 다르다. 소유자가 정해진 프레임에서는 볼 소유자, 정해지지 않은 프레임에서는 공이다.

근접도 = clip( 1 − d ÷ 10m , 0, 1 )

PD (거리항) = 근접도2      PV (속도항) = clip( 접근속도 ÷ 5 , 0, 1 ) × 근접도

PR = 0.6 × PD + 0.4 × PV 접근속도는 거리의 중앙차분에 음수를 붙인 값(가까워지면 +). 근접도를 제곱하는 것은 '붙어 있는 것'에 확실히 더 큰 값을 주기 위해서다.
속도항에도 근접도를 곱하는 이유 — 고쳐진 설계 오류 원래 속도항에는 거리가 전혀 안 들어갔다. 그래서 공에서 40m 떨어진 수비수가 공 쪽으로 5 m/s 로 달리기만 해도 PV=1 → PR=0.4 가 나왔고, 이는 소유자에게 1m 까지 붙어 자리를 지킨 수비수(PR=0.486)와 거의 같았다.
모사 경기에서 재 보니 25m 밖에서 쌓인 값이 PR 총량의 50%였고, 선언한 가중치는 60:40 인데 실제 기여는 거리 18 : 속도 82 였다. 먼 거리에서의 복귀 주력은 '압박'이 아니라 '활동량'이다.
상황PDPVPR해석
소유자에게 3m, 2 m/s 로 접근0.490.280.406제대로 된 압박
소유자에게 1m, 정지(자리 지킴)0.810.000.486붙어서 막고 있음

결과표에는 PR_zone(압박권 안에 있던 프레임 비율 = 관여의 양)과 PR_in(관여했을 때의 평균 PR = 관여의 질)이 따로 나온다. PR 평균 하나에는 이 둘이 섞여 있어 수비형 미드필더와 센터백이 구분되지 않기 때문이다.

10.6 PA — 패스 유인도

성분정의의미
l 길목 개방도clip( 패스선까지 최소 수직거리 ÷ 3m , 0, 1 ) 소유자와 나를 잇는 직선을 수비수가 얼마나 막고 있나. 수선의 발이 선분 안에 있는 수비수만 센다 — 뒤쪽이나 너머의 수비수가 길을 막는 것으로 잘못 계산되는 것을 막는다.
φ 수신 공간clip( 최근접 수비수 거리 ÷ 8m , 0, 1 )공을 받았을 때 자유로운가.
π 전진 가치0.3 + 0.7 × (clip(이득 ÷ 30m, −1, 1) + 1) ÷ 2 이득 = (소유자의 골대까지 거리) − (내 골대까지 거리). 후방 패스도 0 은 아니므로 하한 0.3.
PA = la × φb × πc   (기본 a=b=c=1) 곱셈 모델이라 하나라도 0 이면 전체가 0. 아무리 자유롭고 전진하는 자리라도 패스길이 막혀 있으면 선택지가 아니라는 뜻이고, 축구의 상식과 맞는다.

예 — 길목 1.5m(=0.5), 최근접 수비수 4m(=0.5), 전진 이득 15m(=0.825) → PA = 0.206

전진 가치를 X 좌표가 아니라 '골대까지 거리'로 재는 이유

X 성분만 보면 측면으로 벌리는 전환 패스나 대각 패스가 전부 '전진 0'으로 깎인다. 실제 빌드업의 상당 부분이 그 대각·측면 전환이고, 골문에서 먼 측면으로 가는 패스와 골문 정면으로 파고드는 패스는 가치가 분명히 다르다. 골대까지의 유클리드 거리 감소로 재면 두 경우가 자연히 구분된다.

지수 학습 — 채택 조건이 엄격하다

곱셈 모델에 로그를 씌우면 선형모델이 되므로, 실제 패스를 정답 삼아 로지스틱 회귀로 지수를 추정할 수 있다. 양성은 "실제로 공을 받은 선수", 음성은 "같은 프레임의 나머지 아군"이다. 다만 채택하려면 넷을 다 넘어야 한다.

  • 패스 표본 200개 이상
  • 패스 단위 70/30 분할 후 학습에 안 쓴 패스로 AUC 측정 (검증용 50개 미만이면 포기)
  • 순열검정 — 정답을 무작위로 섞었을 때의 개선 분포를 60회 만들어 그 95% 지점을 넘어야 한다
  • 길목 계수가 음수면(신호가 뒤집힘) 무조건 기각
이 장치가 막아 주는 것 예전 문턱은 30개였는데, "패스 상대가 무작위인" 모사 데이터에서 패스 44개로 AUC 0.387 → 0.613 이 나와 순열검정까지 넘고 채택된 적이 있다. 존재하지 않는 신호를 학습한 것이다. 한 번 채택되면 모든 PA 값이 그 지수로 다시 계산되므로 TC 순위까지 잡음이 된다.

10.7 합성 — DPI · TC · TC_adj

DPI = 0.5 · z(SC) + 0.5 · z(PR)

TC = ⅓ · n(SC) + ⅓ · n(PR) + ⅓ · n(PA)    n( ) = 순위 정규화 z 가 아니라 순위 기반을 기본으로 쓰는 이유: SC 는 좌우대칭인데 PR 은 오른쪽으로 길게 늘어져 있다(왜도 +1.2, 최대/중앙 6.5). z 로 더하면 꼬리가 긴 PR 의 극단값이 합계를 끌고 가서 가중치는 1/3씩인데 실제 영향력은 그렇지 않게 된다.

합치기 전에 빼는 것

  • 골키퍼 — 위험도가 최대인 골문 앞에 상시 서 있어 가만히 있어도 SC 를 쓸어담는다(모사 경기에서 SC 3위/7위). 자기 골대까지 평균거리 22m 미만인 '팀당 한 명'을 골키퍼로 본다(실측: 골키퍼 ~20m, 센터백 ~31m). 검출기가 골키퍼를 알려주면 그것을 우선한다 — tracks.csv 의 class_name 이 여기 쓰인다.
  • 표본이 너무 적은 선수 — 팀 중앙값의 20% 미만. 평균이 튀는 것도 문제지만, 더 큰 문제는 그 값이 정규화 기준까지 흔들어 남의 점수를 바꾼다는 것이다.

TC_adj — 포지션 보정

TC 는 '어느 자리에서 뛰는가'와 상관이 크다. 실측 순위상관은 SC 가 ρ=−0.87(뒤에 설수록 높음), PR 이 +0.68, PA 가 +0.29 다. 그래서 TC 를 '자기 골대까지 평균거리'로 회귀한 잔차를 함께 낸다.

두 숫자를 읽는 법 TC = 팀에 준 총량  ·  TC_adj = 같은 위치의 선수들과 비교했을 때
둘 중 하나가 정답이 아니다. 둘이 많이 다르면 그 순위는 포지션이 만든 것이라는 뜻으로 읽는다. 코드는 TC 의 몇 %가 거리 하나로 설명되는지(R²)를 매번 출력하고 40%를 넘으면 경고한다.

가중치에 대한 태도

0.5/0.5 와 1/3씩은 모두 "검증 전 기준선"이다. 어느 하나가 더 중요하다는 선험적 근거가 없고, 기존 선수 순위에 맞춰 가중치를 조정하면 결론을 먼저 정해 놓고 식을 맞추는 것이 되기 때문이다. 대신 실행할 때마다 "가중치를 바꿨을 때 순위가 얼마나 흔들리는지"를 출력한다.

11 장두 단계 사이 — 끊어져 있는 여섯 곳

여기부터는 코드를 읽기만 한 것이 아니라 실제로 실행해서 확인한 내용이다. tracker.py 가 내는 CSV 열 목록을 기여도 코드의 열 인식 함수에 그대로 넣어 보고, 공 판정 함수에 실제 값을 넣어 봤다.

11.1 좌표가 픽셀이다 가장 심각

CSV 의 fx, fy 주석과 README 모두 "지면 좌표로 바꿀 때 이 값을 쓴다"고 적혀 있다. 그런데 변환 자체가 구현되어 있지 않다. tracker.py 2,593행 어디에도 homography · perspective · warp · 미터 변환이 없다.

기여도 코드는 픽셀을 받으면 스스로 멈춘다.

좌표 범위가 경기장보다 훨씬 크다 (X 0~1920, Y 0~1080).
화면 픽셀 좌표로 보인다. 호모그래피로 미터 좌표로 변환한 뒤에 넣어야 한다.
픽셀로 계산하면 화면 위/아래의 1m 가 서로 달라져서 결과가 전부 무의미해진다.
왜 픽셀로는 절대 안 되는가 카메라는 경기장을 비스듬히 본다. 그래서 화면 아래쪽(가까운 곳)의 100픽셀과 위쪽(먼 곳)의 100픽셀이 서로 다른 거리다. 가까운 쪽에서 5m 인 간격이 먼 쪽에서는 20m 일 수 있다.

기여도 계산의 거의 모든 상수가 미터 기준이다 — 격자 1m, 위험도 감쇠 18m·20m, 압박권 10m, 패스 길목 3m, 수신 공간 8m, 소유 반경 2~8m, 최고속도 11 m/s. 픽셀을 넣으면 이 상수들이 화면 위치에 따라 제멋대로 늘어났다 줄었다 한다. 계산은 조용히 끝나지만 숫자는 전부 무의미하다.

11.2 열 이름이 맞지 않는다 실행 확인

tracker.py 의 CSV_COLUMNS 를 기여도 코드의 map_columns() 에 넣고 돌린 결과다.

열 인식: frame ← 'frame' , time_s ← 'time_sec' , track_id ← 'track_id' ,
        conf ← 'conf' , team ← 'team'

인식된 표준 열 : ['frame', 'time_s', 'track_id', 'conf', 'team']
필수 열 중 없는 것 : {'X', 'Y'}          ← 여기서 멈춘다

기여도 코드의 별칭 목록에 x, pos_x, pitch_x 는 있지만 cx · fx 는 없다. class_name · class_id 도 cls 로 인식되지 않아, 심판 제외와 골키퍼 자동 지정이 작동하지 않는다. 변환 단계에서 이름만 바꿔 주면 해결된다.

11.3 팀 번호 규약이 다르다

tracker 는 0 / 1 / -1 / 빈칸(공)을 쓴다. 기여도 코드는 팀이 정확히 2개여야 하고, 심판으로 인식하는 키워드는 ref, 심판, none, nan, unknown 이다. -1 은 이 목록에 없으므로 세 번째 팀으로 세어지고 다음에서 멈춘다.

팀이 2개여야 하는데 ['0', '1', '-1'] 이다. team 열을 정리할 것.
단순히 -1 을 다 빼면 안 된다 축구 전용 모델은 골키퍼도 team=-1 로 표시한다(팀 색 군집에서 빠지므로). -1 을 통째로 빼면 골키퍼까지 사라진다. 그러면 골문 앞 공간을 센터백이 대신 받아 SC 가 부풀려지고, 기여도 코드의 골키퍼 제외 로직도 대상을 못 찾는다.
올바른 처리: class_name == 'referee' 인 행만 빼고, goalkeeper 는 남긴다. 그리고 그 track_id 목록을 기여도 코드의 GK_IDS 에 직접 넣는다(자동 추정보다 정확하다).

11.5 interpolated 열이 무시된다 경미

tracker 는 보간으로 메운 공 위치를 interpolated=1, conf=0 으로 정직하게 표시한다. 그런데 기여도 코드는 그 열을 읽지 않고 자기만의 보간을 따로 한다. 결과적으로 추정 위치와 측정 위치가 똑같은 자격으로 소유자 판정에 쓰인다. 치명적이지는 않지만, 어느 기여가 실측에서 나왔는지 구분할 수단이 사라진다. conf 열은 인식되므로, 기여도 코드의 BALL_MIN_CONF 를 0보다 크게 두면 보간 행(conf=0)만 자연히 빠진다.

11.6 공 높이 정보가 없다 경미

기여도 코드에는 공중볼(높이 1.5m 초과) 구간을 소유자 판정에서 빼는 장치가 있는데, tracks.csv 에는 높이 열이 없어 작동하지 않는다. 크로스·헤더 경합 구간에서 지면상 가장 가까운 선수가 소유자로 잡힌다. 단안 카메라로 공 높이를 추정하는 것은 별도 연구 주제이므로, 지금은 "그런 한계가 있다"로 알아 두면 된다.

13 장고치는 순서

네 가지를 이 순서로 해야 한다. 앞의 것을 안 고치고 뒤의 것을 고치면 헛수고가 된다.

1순위 · 픽셀 → 미터 변환 (호모그래피)

이것 없이는 나머지가 전부 무의미하다. 경기장의 알려진 지점 4개 이상을 화면에서 찍어 두 평면 사이의 변환 행렬을 구한다.

import cv2, numpy as np, pandas as pd

# 화면에서 찍은 점 (픽셀)                  실제 경기장 위치 (미터)
src = np.float32([[412, 880], [1503, 872], [1740, 402], [188, 410]])
dst = np.float32([[  0,  0], [ 105,   0], [ 105,  68], [  0,  68]])
H, _ = cv2.findHomography(src, dst)

df  = pd.read_csv("results/경기/tracks.csv")
pts = np.float32(df[["fx", "fy"]].values).reshape(-1, 1, 2)
xy  = cv2.perspectiveTransform(pts, H).reshape(-1, 2)
df["X"], df["Y"] = xy[:, 0], xy[:, 1]

쓸 만한 기준점: 경기장 네 모서리, 페널티박스 네 모서리, 골에어리어 모서리, 하프라인과 터치라인이 만나는 두 점, 센터서클 좌우 끝.

중계 영상이면 이것만으로 부족하다 — 제작자도 같은 결론을 적어 두었다 위 방법은 카메라가 고정일 때만 한 번으로 끝난다. 중계 카메라는 패닝·줌·틸트를 하므로 프레임마다 변환 행렬이 달라진다. 선택지는 셋이다.

3순위 · 변환 스크립트 (tracks.csv → 기여도 입력)

11장의 나머지를 한 번에 처리하는 30~40줄짜리 스크립트다. 하는 일은 여섯 가지다.

  1. 공 행(track_id ≥ 1,000,000 또는 class_name == 'ball')을 떼어 ball_x, ball_y 로 만든다 — 공은 cx, cy 를 쓴다
  2. 사람 행에서 class_name == 'referee' 만 뺀다 (골키퍼는 남긴다)
  3. fx, fy 에 호모그래피를 적용해 X, Y(미터)를 만든다
  4. team 0/1 을 알아보기 쉬운 이름으로 바꾼다 (예: Home / Away)
  5. 골키퍼 track_id 목록을 뽑아 기여도 코드의 GK_IDS 에 넣는다
  6. 보간 행을 뺄 생각이면 interpolated == 1 을 거르거나 기여도 코드의 BALL_MIN_CONF 를 0.01 이상으로 둔다

4순위 · 기여도 코드 쪽 정리

  • 궤적 잇기(track stitching) — 시간이 겹치지 않으면서 끝점과 시작점이 시공간적으로 이어지는 조각을 하나로 합친다. 1~3순위를 해도 완벽한 추적은 없으므로, 남는 파편을 해석 단계에서 흡수하는 장치다. 지금 코드에는 없다.
  • 표 정리 — 관측이 너무 적은 조각은 화면 표에서 빼고(엑셀에는 남기고), NaN 을 – 로 표시하고, 22행 남짓만 보이게 한다.
  • TC 를 부분 지표로도 계산 — 세 지표가 다 없으면 지금은 NaN 인데, 있는 것끼리 가중치를 다시 나눠 계산하고 "무엇으로 계산했는지"를 함께 표시하면 짧은 클립에서도 쓸 수 있다.

14.2 제작자가 밝힌 한계 (README 6장)

한계이 문서의 대응
전술 카메라 기준으로 맞췄다. 일반 중계 화면에서는 리플레이·클로즈업에서 결과가 흔들린다 13장 1순위와 정확히 같은 결론. 호모그래피도 고정 카메라를 전제해야 쉽다.
공 발견률은 전술 카메라 1080p 기준 약 75~80% 기여도의 소유자 판정이 그만큼만 가능하다는 뜻. usable 비율의 상한이 여기서 정해진다.
골키퍼는 영상에서 GK 로 통일되지만 CSV 의 track_id 는 가려졌다 나오면 바뀔 수 있다 기여도 코드의 골키퍼 자동 추정이 실패하는 원인. GK_IDS 직접 지정으로 대응한다.
CPU만으로는 느리다. 전체 경기는 밤새 돌리는 용도 실측 CPU 8코어 1080p '빠르게' = 영상 길이의 약 5배(45분 경기 ≈ 4시간).
관중석이 초록인 경기에서는 잔디 구분이 안 돼 경기장 밖 인물이 덜 걸러진다 해가 없는 쪽으로 실패한다(아무것도 안 거른다). 다만 기여도의 SC 는 영향을 받는다.

14.3 이 문서가 덧붙이는 한계

  • 픽셀 좌표 — 지면 좌표 변환이 미구현(11.1). 기여도 계산의 전제가 성립하지 않는다.
  • 공 높이 없음 — 크로스·헤더 경합에서 소유자 판정이 틀어진다(11.6).
  • ID 지속 — 현재 설정에서 선수별 집계가 성립하지 않는다(12장).
  • 한 화면의 한계 — 카메라 한 대로는 경기장의 2/3 만 담긴다. SC 는 경기장 전체 격자를 나누는 계산이라 이 부분이 구조적 제약이다.

15 장용어 사전

용어뜻
검출 (Detection)한 장의 이미지에서 "여기에 사람이 있다"를 찾는 것. 프레임 사이의 관계는 모른다.
추적 (Tracking)프레임을 가로질러 "이 사람과 저 사람이 같은 사람"임을 잇는 것. 그 결과가 track_id.
ByteTrack검출 결과를 잇는 추적 알고리즘. 칼만 필터로 다음 위치를 예측하고 박스 겹침(IoU)으로 짝짓는다. 낮은 신뢰도 검출도 2단계로 활용하는 것이 특징이다.
IoU두 박스의 겹친 넓이 ÷ 합친 넓이. 1이면 완전히 같고 0이면 안 겹친다.
헝가리안 매칭N개와 M개를 짝지을 때 전체 비용 합이 최소가 되는 짝을 찾는 알고리즘. lap 이 이것을 한다.
칼만 필터지금까지의 움직임으로 다음 위치를 예측하는 방법. 검출이 잠깐 없어도 추적을 이어 준다.
호모그래피한 평면(화면)의 점을 다른 평면(경기장)으로 옮기는 3×3 변환 행렬. 기준점 4개면 구할 수 있다.
HSV / Lab색을 표현하는 좌표계. HSV 는 색상·채도·명도(잔디 찾기에 씀), Lab 은 밝기(L)와 색(a·b)이 분리되어 그늘의 영향을 뺄 수 있다(팀 구분에 씀).
k-means점들을 k 개 덩어리로 묶는 군집 알고리즘. 여기서는 상체 색을 4덩어리로 묶어 두 팀을 찾는다.
모폴로지 연산마스크의 구멍을 메우거나(CLOSE) 잔점을 지우는(OPEN) 영상 처리 연산.
Shapley 값여럿이 협력해 만든 성과를 각자의 기여에 따라 나누는 협력게임 이론의 배분 방식. 합이 보존되고(효율성) 같은 기여는 같은 몫을 받는다(대칭성).
z 점수 / 순위 정규화단위가 다른 값을 비교 가능하게 만드는 방법. z 는 (값−평균)÷표준편차, 순위 정규화는 순위를 정규분포 점수로 바꾼다. 후자는 분포 모양에 안 휘둘린다.
AUC어떤 점수가 두 부류를 얼마나 잘 가르는지를 0.5~1 로 나타낸 값. 0.5는 동전 던지기, 1은 완벽.
순열검정정답을 무작위로 섞은 가짜 데이터에서도 같은 성능이 나오는지 확인하는 검정. "우연히 좋아 보이는 것"을 걸러낸다.
OpenVINO인텔이 만든 CPU 추론 가속 라이브러리. 모델을 한 번 변환해 두면 1.5~2배 빨라진다.
usable기여도 계산에 실제로 쓰인 프레임. 소유팀이 정해졌고 양 팀 인원이 충분히 추적된 프레임.
