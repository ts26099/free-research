좌표 → 기여도

"그 위치에 서 있던 것이 팀에 얼마나 도움이 되었는가"를 답한다. 축구 전술과 통계 문제다. 공간 분할, 협력게임 배분, 순위 정규화.

2 장측정 단계 (1) — 준비와 조작

2.1 bootstrap.py — 설치 순서가 곧 결과 품질이다

이 파일은 한 번만 도는 설치 스크립트다. 그런데 여기 적힌 순서가 나중의 데이터 품질을 직접 결정한다. 평범한 설치 스크립트가 아니라는 뜻이다. 중요한 대목이 세 곳 있다.

(1) torch 를 ultralytics 보다 먼저 설치한다

gpu = has_nvidia_gpu()                      # nvidia-smi 가 도는지로 판단
if gpu:  pip install torch torchvision --index-url .../whl/cu124
else:    pip install torch torchvision      # CPU 판
pip install ultralytics                     # ← 반드시 torch 다음

ultralytics 를 먼저 깔면 의존성 해결 과정에서 CPU 전용 torch 휠을 끌어온다. 그러면 GPU 가 있는 PC 인데도 CPU 로 돌아가고, 45분 영상 분석이 몇 분에서 몇 시간으로 늘어난다. 코드에 "torch 를 먼저 깔아둬야 ultralytics 가 제멋대로 CPU 휠을 끌어오지 않는다" 라고 적혀 있는 이유다.

(2) lap 을 미리 설치한다 — 안 하면 첫 분석의 track_id 가 전부 -1 이 된다

pip install lap    # ByteTrack 의 헝가리안 매칭에 필요
이것이 왜 치명적인가 lap 이 없으면 ultralytics 가 첫 추적 도중에 알아서 설치를 시도하는데, 그 회차는 추적이 작동하지 않아 track_id 가 전부 -1 로 나온다. track_id 가 -1 이면 "같은 선수"라는 개념이 사라지고, 기여도 계산은 선수별 집계 자체가 불가능해진다. 몇 시간을 돌리고도 쓸 수 없는 CSV 가 나온다. 그래서 설치 시점에 미리 넣는다.

(3) 실패해도 되는 것과 아닌 것을 구분한다

OpenVINO(CPU 가속)와 tkinterdnd2(드래그앤드롭)는 설치에 실패해도 그냥 넘어간다. 없어도 프로그램이 도는 것들이다. 반면 torch · ultralytics · lap 은 실패하면 venv 를 통째로 지우고 중단한다. 반쯤 설치된 환경을 남기지 않기 위해서다.

이 구분이 중요한 이유는, 코드의 거의 모든 필터가 "모델이 안 알려주는 것을 대신 알아내는 장치"이기 때문이다. 축구 전용 모델을 쓰면 그 필터들 중 절반은 할 일이 없어진다.

3.2 추적 — 같은 선수에게 같은 번호를 유지하기

검출만으로는 "이 프레임의 3번 상자"와 "다음 프레임의 5번 상자"가 같은 사람인지 알 수 없다. ByteTrack 이 그 연결을 맡는다. 코드는 두 가지를 손봤다.

auto_tracker_thresh — 사용자가 정한 신뢰도의 의미를 지킨다

ByteTrack 의 내부 임계값은 0.25 로 고정되어 있다. 그래서 사용자가 conf 를 0.10 으로 낮춰도 0.25 미만 검출은 추적 번호를 못 받고 버려진다. 이 옵션을 켜면 임계값을 conf 에 맞춰 다시 계산한 트래커 설정 파일을 자동 생성해 쓴다.

match_thresh 0.9 — 작은 박스 영상에서 트랙이 끊기는 문제

코드에 적힌 실측 (20초 구간, 두 영상) 720p 영상에서 선수 키가 32px 이면 몸통 너비는 13px 남짓이다. 프레임간격 3이면 처리 간격이 0.125초라 달리는 선수가 그 사이에 자기 너비만큼 움직인다. 박스 겹침이 0 이 되어 트랙이 끊기고 새 번호를 받는다. 그 영상에서 트랙 지속 중앙값이 2장(0.2초)이었다.

0.8 → 0.9 로 올린 뒤 :
  · 사용자 720p : 추적ID 233→139개 · 트랙 지속 7→13장 · 검출 15.8→17.9명
  · 전술 1080p : 추적ID 189→117개 · 트랙 지속 13→24장 · 검출 18.1→19.3명
임계값을 풀면 다른 선수로 옮겨붙을 위험이 생기는데, 그것도 따로 쟀다 — 트랙 안에서 자기 키보다 크게 튄 비율이 두 영상·세 설정 모두 0.0% 였다. ByteTrack 이 칼만 필터 예측을 함께 쓰기 때문이다.

이 숫자를 기억해 두자. 트랙 지속이 13~24장, 즉 1~2초다. 7장에서 다시 나온다.

3.3 사람 거르기 — 경기장 밖과 화면에 박힌 그래픽

잔디 마스크 (pitch_mask)

HSV 색상 범위(기본 30~95)로 잔디를 찾아 마스크를 만들고, 가장자리를 16px 안쪽으로 좁힌 뒤, 사람 상자의 발밑 점이 마스크 밖이면 버린다. 30프레임마다 다시 계산하고, 리플레이·클로즈업처럼 잔디를 못 찾는 프레임에서는 직전 마스크를 유지한다.

중심점이 아니라 발밑 점을 쓰는 이유가 중요하다. 사람은 땅을 딛고 서 있으므로 지면 위치는 발이다. 중심점을 쓰면 키 큰 사람이 경기장 안에 있어도 밖으로 판정되는 일이 생긴다. 공에는 이 필터를 적용하지 않는다 — 공은 공중에 뜨기 때문이다.

정지 그래픽 트랙 (static_tracks)

하단 배너나 선수 소개 그래픽에 박힌 사진도 YOLO 에는 사람으로 보인다. 그런데 그건 화면에 붙박여 있어서 카메라가 움직여도 제자리다. 판정 규칙은 이렇다.

(이동 폭 ÷ 평균 키) < 0.10  이고  등장 횟수 ≥ 15프레임  →  사람이 아니라 그래픽 이동 폭을 키로 나누는 이유: 멀리 있어 작게 잡힌 선수도 같은 자로 재기 위해서다. 픽셀 거리를 그대로 쓰면 먼 곳의 진짜 선수가 '안 움직인 것'으로 걸린다.

3.4 팀 나누기 — 유니폼 색으로 두 팀을 가른다

심판은 경기장 안에서 뛰므로 위치로는 못 거른다. 그래서 색을 쓴다. 4단계다.

단계하는 일세부
①상체 색 뽑기
torso_color()		 상자에서 위 15~50% · 가운데 절반만 잘라낸다(머리와 다리를 뺀다). 그중 잔디 초록 픽셀을 빼고, 남은 픽셀의 Lab 색공간 a·b 두 채널 중앙값을 그 사람의 색으로 삼는다. 밝기(L)를 버리는 것이 핵심이다 — 그늘에 들어간 선수와 햇빛 아래 선수를 같은 색으로 묶기 위해서다.

④트랙 단위 확정
_decide_team()		 프레임마다 따로 판정하면 한 선수의 팀이 0→-1→1 로 깜빡인다(겹침·모션블러 한 번이면 넘어간다). 분석이 끝난 뒤 track_id 별 다수결로 team 열을 한 번에 통일한다. 동률이면 -1 보다 실제 팀(0/1)을 우선한다 — 멀어서 상체가 안 잡힌 프레임이 -1 로 세어지기 때문이다.
초록 유니폼 문제 — 필터가 상체를 통째로 지우는 경우 ①에서 "잔디 초록을 뺀다"는 단계가 유니폼이 초록 계열일 때 상체를 전부 지워 버린다. 실측 — 브라질(노랑) 대 멕시코(초록) 영상에서 상체 36개를 재니 36개 전부가 잔디로 판정됐다. 초록 유니폼은 당연하고, 노란 유니폼도 색조가 34 라 잔디 범위(30~95) 하한 안쪽에 들어갔다. 그 결과 팀 보정 표본이 342명 중 41명으로 줄고 96%가 미분류됐다.

그래서 torso_grass_fallback 이 있다 — 남는 픽셀이 12개 미만이면 지우지 말고 패치 전체를 쓴다. 상체 패치는 원래 대부분이 유니폼이라 잔디가 조금 섞여도 중앙값이 버틴다. 같은 영상에서 표본이 41 → 342명으로 돌아왔다.

3.5 골키퍼 — 모델이 골대 기둥을 골키퍼라고 부른다

가장 흥미로운 필터다. 축구 전용 모델은 골키퍼를 프레임마다 '골키퍼'와 '선수'로 오간다. 실측하니:

  • 진짜 골키퍼 트랙은 골키퍼 라벨이 3~39%뿐이고 나머지는 선수 라벨이었다.
  • 반대로 골대(세로 기둥·그물)는 골키퍼 라벨이 69~100%였다. 학습 데이터에서 골키퍼가 늘 골대 옆에 서 있어서 모델이 "기둥 = 골키퍼"로 배운 것이다.

그래서 프레임 단위로는 판정하지 않고, 골키퍼 라벨이 한 번이라도 붙은 트랙을 트랙 단위로 가른다(resolve_keeper_tracks).

조건판정
유니폼 색이 팀 0 또는 1 이다필드 선수 — 골대 근처에서 잠깐 잘못 찍힌 것. 골키퍼 라벨을 선수로 되돌린다.
팀 -1 이고, 트랙 전체 신뢰도 중앙값 < 0.50골대 — 선수 라벨 행까지 트랙을 통째로 뺀다.
그 외골키퍼 — 트랙 전체를 골키퍼로 통일한다.

임계값 0.50 의 근거: 트랙 전체 신뢰도 중앙값이 골대는 0.22~0.41, 골키퍼는 0.60~0.81 이었다. 골키퍼 라벨이 붙은 행만 보면 0.41 / 0.45 로 거의 붙어 있는데, 진짜 골키퍼는 선수로 찍힌 행의 신뢰도가 높아 트랙 전체로 보면 0.41 / 0.60 으로 벌어진다. 그 사이인 0.50 에서 자른다.

3.6 공 — 여섯 단계를 거친다

이 프로그램에서 가장 공들인 부분이다. 이유는 간단하다. 공 위치가 틀리면 기여도가 통째로 틀린다. 공이 어디 있느냐로 "누가 소유자인가", "어느 팀이 공격 중인가", "위험한 공간이 어디인가"가 전부 결정되기 때문이다.

왜 이렇게까지 하는가 — 실측 오검출 리버풀-레알 경기 50초 구간을 눈으로 전수 판정한 결과, 공 검출 587건 중 281건(48%)이 페널티 마크였다. 게다가 마크가 잡히는 프레임에서는 진짜 공을 대신 놓치는 일이 많았다. 무작위 104건 판정에서는 흰 축구화가 19건(18%)으로 가장 큰 오류였다.

① 공 전용 모델을 따로 돌린다

선수 모델은 공을 잘 못 찾는다. 공은 지름 12px 남짓이라 선수와 함께 학습된 모델에서는 늘 뒷전이다. 같은 60프레임 실측: 선수 모델 @1280 은 42장에서 발견하고 968ms/장, 공 전용 모델 @1280 은 50장에서 발견하고 134ms/장 — 더 잘 찾으면서 7배 빠르다. 공 전용 모델의 track_id 는 1,000,000번부터 매겨 선수 번호와 섞이지 않게 한다.

② 직전 공 위치를 확대해 한 번 더 본다 (ball_focus)

먼 공이나 선수 발밑의 공은 전체 화면에서 몇 픽셀이라 신뢰도가 바닥이다. 직전 위치 주변 480px 를 잘라 960 으로 2배 키워 다시 보면 같은 공을 0.04 → 0.7~0.8 로 잡는다. 공을 놓친 지 2초가 지나면 그만 본다.

③ 네 가지 물리 검사

검사기준근거

밝기 검사에는 면제 규칙이 딸려 있다. 날아가는 공은 모션블러로 흰색이 번져 밝기가 190~210 으로 떨어지기 때문이다. 신뢰도 0.70 이상이면 밝기 검사를 면제하되, 면제에도 바닥(180)을 두고, 움직이는 후보에게만 면제를 준다 — 멈춘 공은 번지지 않으므로 밝게 찍히고, 페널티 마크는 제자리에 있기 때문이다.

④ 후보가 여럿이면 하나만 고른다 (BallPicker)

근거는 "경기장에 공은 하나뿐"이라는 사실이다. 직전 위치에서 등속으로 예측한 자리에 가까운 후보에게 점수를 얹는다.

점수 = 신뢰도 + 0.6 × exp( −예측위치까지의 거리 ÷ 140px ) 페널티 마크는 늘 제자리라 예측에서 벗어나고, 진짜 공은 매끄럽게 움직여 예측에 맞는다. 실측: 프레임간 이동폭 90% 지점이 102px → 69px 로 줄었다.
스스로 강화되는 함정과 그 해법 연속성 보너스(최대 0.6)가 신뢰도 차이보다 크면 문제가 생긴다. 한번 페널티 마크에 물리면 마크는 늘 제자리라 보너스를 통째로 받고, 멀리 튄 진짜 공은 보너스를 못 받아 영영 빠져나오지 못한다.
실측 f342 — 진짜 공 0.79+0.00=0.79 / 페널티 마크 0.54+0.56=1.10 ← 이것이 뽑혔다.

그래서 "훨씬 확신하는 후보가 있으면 갈아탄다"(ball_switch_margin 0.20)는 장치를 뒀다. 선택이 갈린 19개 프레임을 전수 확인하니 19개 모두 갈아탄 쪽이 진짜 공이었다. 갈아탄 직후에는 속도를 0으로 초기화한다 — 옛 자리에서 새 자리까지의 거리를 속도로 삼으면 다음 예측이 엉뚱한 곳을 가리켜 다시 마크로 되돌아가기 때문이다.

⑤ 궤적 잇기 (chain_ball) — 시간축으로 진짜 공을 가려낸다

한 프레임만 보면 달리는 선수의 흰 축구화는 공과 구별되지 않는다(밝기 222~250, 채움 0.62~0.83, 크기비 0.20~0.27 — 전부 공 범위). 차이는 시간축에 있다. 진짜 공의 약한 후보들은 서로 이어져 확실한 공으로 연결되지만, 축구화는 어떤 확실한 공과도 이어지지 않는다.

그래서 신뢰도 0.60 이상으로 잡힌 공을 끝점으로 삼아 앞뒤로, 검사에서 탈락한 후보까지 포함해 등속 예측을 따라간다. 이어진 길이가 3 이상이면 그 프레임의 선택을 바꾼다. 실측 오프라인 재현에서 교체 84건 · 추가 161건, 교체 78건을 비교하니 좋아진 것 약 50, 나빠진 것 약 5 였다.

⑥ 짧은 공백 메우기 (interpolate_ball)

앞뒤로 확실히 잡힌 위치 사이를 직선으로 잇는다. 여기서 중요한 것은 상한을 0.4초로 잡은 근거다.

5.1 무엇을 재려는 것인가

골·어시스트·패스 성공률은 공에 닿은 사람만 기록한다. 그런데 축구에서 일어나는 일의 대부분은 공 없이 일어난다. 수비수가 공간을 미리 막아서 패스 선택지를 지운 것, 미드필더가 소유자에게 붙어 시간을 빼앗은 것, 공격수가 좋은 자리에 서 있어서 수비를 끌고 간 것 — 이런 것은 어떤 기록지에도 안 남는다. 이 프로그램이 재려는 것이 그것이고, 세 축으로 나눈다.

지표무엇을언제 나오나한 줄 정의

SC·PR 과 PA 는 서로 다른 프레임에서 나온다 이 점이 결과표를 읽을 때 계속 걸린다. 우리 팀이 공을 갖고 있는 동안 우리 선수에게는 PA 만 쌓이고 SC·PR 은 쌓이지 않는다. 그래서 양 팀이 공수를 주고받는 구간이 충분히 있어야 세 지표가 다 모인다. 짧은 클립에서 한 팀이 계속 공을 갖고 있었다면 한쪽은 수비 기록이, 다른 쪽은 공격 기록이 아예 없어서 TC 를 낼 수 없다. 지난번 결과표에서 TC 가 대부분 비어 있던 이유 중 하나다.

순서단계내용

5.3 공 소유 판정 — 모든 계산의 기준점

프레임마다 "지금 누가 공을 갖고 있나 / 어느 팀이 공격 중인가"를 정한다. 이것이 정해져야 SC 의 수비팀, PR 의 목표물, PA 의 패스 시작점이 정해진다.

  1. 가장 가까운 선수를 찾는다. 그 거리가 POSS_RADIUS(데이터를 보고 2~8m 중 자동 결정) 이내면 소유자로 인정한다.
  2. 데드볼 제외 — 공이 라인 밖 1m 를 넘어가면 소유자를 두지 않는다. 90분 경기에서 공이 실제로 살아 있는 시간은 55~60분뿐이고, 스로인을 기다리며 자리 잡는 배치를 전술적 공간 다툼으로 계산하면 안 되기 때문이다.
  3. 공중볼 제외 — 공 높이 열이 있고 1.5m 를 넘으면 소유자를 두지 않는다. 크로스·헤더 경합은 점프와 타이밍으로 결정되므로 지면 2D 거리로는 소유자를 정할 수 없다.
  4. 전환 인정 조건 — 소유팀이 바뀌었다고 바로 인정하지 않는다. 1.5초(HOLD_FRAMES)보다 짧으면서 앞뒤가 같은 팀인 구간은 잡음으로 보고 흡수한다. A→B→A 의 짧은 B 는 지우고, A→B→C 의 B 는 실제 전환이므로 남긴다.
  5. usable 판정 — 소유팀이 정해졌고 양 팀 모두 최소 인원(명목 인원의 80%)이 추적된 프레임만 계산에 쓴다.
usable 이 왜 필요한가 SC 는 경기장 전체 격자를 "가장 가까운 수비수"에게 나눠 주는 계산이다. 뒤쪽 수비수가 화면 밖으로 빠지면 남은 수비수가 그 빈 자리의 공간 점유까지 대신 받아 SC 가 부풀려진다. 그래서 인원이 모자란 프레임은 아예 계산하지 않는다. 한 대의 중계 카메라로 만든 좌표는 화면에 경기장의 2/3 정도만 들어오므로, usable 비율이 낮게 나오는 것이 오히려 정직한 신호다.

5.4 SC — 공간 통제 (Shapley 배분)

세 걸음으로 이루어진다.

1걸음 · 경기장을 격자로 자르고 칸마다 위험도를 매긴다

w(칸) = exp( −골대까지거리 ÷ 18 ) × exp( −공까지거리 ÷ 20 ) × 칸넓이 1m × 1m 격자이므로 105 × 68 경기장이면 약 7,140칸이다. "위험하다"는 것은 내 골대에 가깝고 동시에 공에 가깝다는 뜻이다. 둘 중 하나만 만족하는 칸은 값이 급격히 떨어진다. 18m, 20m 는 감쇠 거리로, 그만큼 멀어질 때마다 값이 1/e(약 37%)로 준다.

예: 내 골대에서 20m, 공에서 15m 떨어진 칸 → exp(−20/18) × exp(−15/20) = 0.329 × 0.472 = 0.156. 같은 거리라도 골문 바로 앞(골대 5m, 공 5m)이면 0.757 × 0.779 = 0.590 으로 네 배 가까이 크다.

2걸음 · 각 칸을 누가 통제하는지 정한다

그 칸까지의 거리가 가장 가까운 공격수보다 가까운 수비수들이 그 칸을 통제한다고 본다. 한 명일 수도, 세 명일 수도, 아무도 없을 수도 있다(그 칸은 공격팀 영역이므로 아무에게도 안 간다).

3걸음 · 통제하는 수비수끼리 나눈다 (Shapley)

칸을 함께 덮은 수비수가 k 명이면, 각자 w(칸) ÷ k 씩 가져간다 협력게임 이론의 Shapley 값에서 대칭성과 효율성을 만족하는 배분이다. 효율성: 한 프레임에서 모든 수비수가 받은 SC 의 합은 통제된 총 위험도와 정확히 같다(코드가 매번 검산한다). 대칭성: 같은 칸을 같은 조건으로 덮은 두 수비수는 같은 값을 받는다. 덕분에 "혼자 넓게 막은 수비수"와 "둘이 겹쳐 막은 수비수"가 공평하게 평가된다.

프레임마다 위험도 총량이 크게 다르기 때문에(공이 자기 박스 안이면 총량 320, 상대 박스 쪽이면 29 로 11배 차이), 원값 SC 와 함께 팀 총량 대비 몫인 SC_share 도 낸다. 효율성 공리 덕분에 한 프레임의 share 합은 정확히 1 이다.

5.5 PR — 압박 기여

목표물은 상황에 따라 다르다. 소유자가 정해진 프레임(settled)에서는 볼 소유자, 정해지지 않은 프레임(transition)에서는 공이다. 수비팀 선수마다 목표물까지의 거리 d 와 접근속도를 재서 두 항으로 합친다.

근접도 = clip( 1 − d ÷ 10m , 0, 1 )

PD (거리항) = 근접도2      PV (속도항) = clip( 접근속도 ÷ 5 , 0, 1 ) × 근접도

PR = 0.6 × PD + 0.4 × PV 접근속도는 거리의 중앙차분에 음수를 붙인 값이다(가까워지면 +). 근접도를 제곱하는 것은 "붙어 있는 것"에 확실히 더 큰 값을 주기 위해서다.
속도항에도 근접도를 곱하는 이유 — 고쳐진 버그 원래 속도항은 clip(접근속도/5, 0, 1) 뿐이라 거리가 전혀 안 들어갔다. 그래서 공에서 40m 떨어진 수비수가 공 쪽으로 5 m/s 로 달리기만 해도 PV=1 → PR=0.4 가 나왔고, 이것은 볼 소유자에게 1m 까지 붙어 자리를 지킨 수비수(PR=0.486)와 거의 같은 값이었다.

모사 경기에서 재 보니 25m 밖에서 쌓인 값이 PR 총량의 50%였고, 선언한 가중치는 60:40 인데 실제 기여는 거리 18 : 속도 82 였다. 먼 거리에서의 복귀 주력은 '압박'이 아니라 '활동량'이다. 지금은 속도항에도 같은 근접도를 곱해 10m 밖에서는 두 항 모두 0 이 된다.

결과표에는 PR 평균 외에 두 열이 더 나온다. PR_zone 은 "압박권(10m) 안에 있던 프레임 비율"(관여의 양), PR_in 은 "관여했을 때의 평균 PR"(관여의 질)이다. PR 평균 하나에는 이 둘이 섞여 있어서 수비형 미드필더(양이 많음)와 센터백(양이 없음)이 구분되지 않기 때문이다.

5.6 PA — 패스 유인도

공을 안 가진 공격팀 선수마다, "지금 소유자가 나에게 패스한다면 얼마나 좋은 선택인가"를 세 축으로 잰다.

성분정의의미
l 길목 개방도clip( 패스선까지의 최소 수직거리 ÷ 3m , 0, 1 ) 소유자와 나를 잇는 직선을 수비수가 얼마나 막고 있나. 수선의 발이 선분 안에 있는 수비수만 센다 — 뒤쪽이나 너머의 수비수가 길을 막는 것으로 잘못 계산되는 것을 막는다.
φ 수신 공간clip( 가장 가까운 수비수까지 거리 ÷ 8m , 0, 1 ) 공을 받았을 때 자유로운가.
π 전진 가치0.3 + 0.7 × (clip(이득 ÷ 30m, −1, 1) + 1) ÷ 2 이득 = (소유자의 골대까지 거리) − (내 골대까지 거리). 후방 패스도 0 은 아니므로 하한 0.3.
PA = la × φb × πc   (기본값 a = b = c = 1) 곱셈 모델이라 하나라도 0 이면 전체가 0 이다. 아무리 자유롭고 전진하는 자리라도 패스길이 막혀 있으면 선택지가 아니라는 뜻이고, 이는 축구의 상식과 맞는다.

예: 길목 1.5m(=0.5), 가장 가까운 수비수 4m(=0.5), 전진 이득 15m(=0.825) → PA = 0.5 × 0.5 × 0.825 = 0.206

전진 가치를 X 좌표가 아니라 '골대까지 거리'로 재는 이유

X 성분만 보면 측면으로 넓게 벌리는 전환 패스(스위치)나 대각 패스가 전부 '전진 0'으로 깎인다. 실제 빌드업의 상당 부분이 그 대각·측면 전환으로 이뤄지고, 골문에서 먼 측면으로 가는 패스와 골문 정면으로 파고드는 패스는 가치가 분명히 다르다. 골대까지의 유클리드 거리 감소로 재면 두 경우가 자연히 구분된다.

지수 a, b, c 를 실제 패스에서 학습하는 장치

곱셈 모델에 로그를 씌우면 선형모델이 되므로, 실제로 일어난 패스를 정답 삼아 로지스틱 회귀로 지수를 추정할 수 있다. 양성은 "그 프레임에 실제로 공을 받은 선수", 음성은 "같은 프레임의 나머지 아군"이다. 그런데 채택 조건이 엄격하다.

  • 패스 표본이 200개 이상이어야 학습을 시도한다.
  • 패스 단위로 70/30 분할해 학습에 안 쓴 패스로 성능(AUC)을 잰다. 검증용 패스가 50개 미만이면 포기한다.
  • 그것도 모자라 순열검정을 한다 — 정답을 무작위로 섞었을 때의 AUC 개선 분포를 60회 만들고, 실제 개선이 그 분포의 95% 지점을 넘을 때만 채택한다.
  • 길목 계수가 음수로 나오면(신호가 뒤집혔다는 뜻) 무조건 기각한다.
이 장치가 막아 주는 것 예전 문턱은 30개였는데, "패스 상대가 무작위인" 모사 데이터에서 패스 44개로 AUC 0.387 → 0.613 이 나와 순열검정 문턱까지 넘고 채택된 적이 있다. 존재하지 않는 신호를 학습한 것이다. 한 번 채택되면 모든 PA 값이 그 지수로 다시 계산되므로 TC 순위까지 잡음이 된다. 90분 경기의 팀 패스는 보통 400~700개라 200개는 무리한 요구가 아니다.

5.7 DPI · TC · TC_adj — 합치기

세 지표는 단위도 분포도 다르고(SC 는 위험도 가중 면적, PR·PA 는 0~1), 나오는 프레임도 다르다. 그래서 원값을 더하는 것은 의미가 없고 같은 자로 맞춘 뒤 더해야 한다.

DPI = 0.5 · z(SC) + 0.5 · z(PR)    (수비 합성)

TC = ⅓ · n(SC) + ⅓ · n(PR) + ⅓ · n(PA)    n( ) = 순위 정규화 z 가 아니라 순위 기반을 기본으로 쓰는 이유: SC 는 좌우대칭인데 PR 은 오른쪽으로 길게 늘어져 있다 (왜도 +1.2, 최대/중앙 6.5). z 로 더하면 꼬리가 긴 PR 의 극단값이 합계를 끌고 가서, 가중치는 1/3씩인데 실제 영향력은 그렇지 않게 된다.

합치기 전에 빼는 것

  • 골키퍼 — 위험도가 최대인 골문 앞에 상시 서 있어서 가만히 있어도 SC 를 쓸어담는다(모사 경기에서 SC 3위/7위). 자기 골대까지의 평균거리가 22m 미만인 '팀당 한 명'을 골키퍼로 본다(실측: 골키퍼 ~20m, 센터백 ~31m). 검출기가 골키퍼를 알려주면 그것을 우선한다.
  • 표본이 너무 적은 선수 — 팀 중앙값의 20% 미만으로 관측된 선수는 뺀다. 평균이 튀는 것도 문제지만, 더 큰 문제는 그 값이 정규화 기준까지 흔들어 남의 점수를 바꾼다는 것이다.

TC_adj — 포지션 보정

TC 는 '어느 자리에서 뛰는가'와 상관이 크다. 실측 순위상관은 SC 가 ρ = −0.87(뒤에 설수록 높음), PR 이 +0.68, PA 가 +0.29 였다. 보정 없이는 순위가 능력이 아니라 포지션을 반영한다. 그래서 TC 를 '자기 골대까지의 평균거리'로 회귀한 잔차를 TC_adj 로 함께 낸다.

두 숫자를 읽는 법 TC = 팀에 준 총량.   TC_adj = 같은 위치의 선수들과 비교했을 때.
둘 중 하나가 정답이 아니다. 둘이 많이 다르면 그 순위는 포지션이 만든 것이라는 뜻으로 읽으면 된다. 코드는 TC 의 몇 %가 거리 하나로 설명되는지(R²)를 매번 출력하고, 40%를 넘으면 경고한다.

가중치에 대한 태도

0.5/0.5 와 1/3씩은 모두 "검증 전 기준선"이다. 어느 하나가 더 중요하다는 선험적 근거가 없고, 기존 선수 순위에 맞춰 가중치를 조정하면 결론을 먼저 정해 놓고 식을 맞추는 것이 되기 때문이다. 대신 코드는 실행할 때마다 "가중치를 바꿨을 때 순위가 얼마나 흔들리는지"를 출력한다. 그 값이 낮으면(ρ < 0.5) 가중치가 순위를 지배하고 있다는 뜻이므로, 승패·득점 같은 결과 라벨이 생기면 반드시 다시 정해야 한다.

6 장두 단계 사이 — 지금 끊어져 있는 다섯 곳

여기부터는 코드를 읽기만 한 것이 아니라 실제로 돌려서 확인한 내용이다. tracker.py 가 내는 CSV 열 목록을 기여도 코드의 열 인식 함수에 그대로 넣어 보고, 공 판정 함수에 실제 값을 넣어 봤다.

6.1 좌표가 픽셀이다 — 미터로 바꾸는 코드가 어디에도 없다 가장 심각

CSV 의 fx, fy 주석에는 "지면 좌표 변환용"이라고 적혀 있다. 그런데 변환 자체가 구현되어 있지 않다. tracker.py 2,593행 어디에도 homography · perspective · warp · 미터 변환이 없다.

기여도 코드는 픽셀을 받으면 스스로 멈춘다.

좌표 범위가 경기장보다 훨씬 크다 (X 0~1920, Y 0~1080).
화면 픽셀 좌표로 보인다. 호모그래피로 미터 좌표로 변환한 뒤에 넣어야 한다.
픽셀로 계산하면 화면 위/아래의 1m 가 서로 달라져서 결과가 전부 무의미해진다.
왜 픽셀로는 절대 안 되는가 카메라는 경기장을 비스듬히 본다. 그래서 화면 아래쪽(가까운 곳)의 100픽셀과 위쪽(먼 곳)의 100픽셀이 서로 다른 거리다. 가까운 쪽에서는 5m 일 수 있고 먼 쪽에서는 20m 일 수 있다.

기여도 계산의 거의 모든 상수가 미터 기준이다 — 격자 1m, 위험도 감쇠 18m·20m, 압박권 10m, 패스 길목 3m, 수신 공간 8m, 소유 반경 2~8m, 최고속도 11 m/s. 픽셀을 넣으면 이 상수들이 화면 위치에 따라 제멋대로 늘어났다 줄었다 한다. 계산은 조용히 끝나지만 숫자는 전부 무의미하다.

6.2 열 이름이 맞지 않는다 확인함

tracker.py 의 CSV_COLUMNS 를 기여도 코드의 map_columns() 에 그대로 넣고 실행한 결과다.

열 인식: frame ← 'frame' , time_s ← 'time_sec' , track_id ← 'track_id' ,
        conf ← 'conf' , team ← 'team'

인식된 표준 열 : ['frame', 'time_s', 'track_id', 'conf', 'team']
필수 열 중 없는 것 : {'X', 'Y'}          ← 여기서 멈춘다

기여도 코드의 별칭 목록에 x, pos_x, pitch_x 같은 이름은 있지만 cx · fx 는 없다. 그래서 위치 열을 하나도 못 찾고 "필수 열이 없다: {'X','Y'}" 로 중단된다. class_name · class_id 도 마찬가지로 cls 로 인식되지 않는다.

해결은 간단하다 — 변환 단계에서 fx → X, fy → Y 로 이름만 바꿔 주면 된다(단위는 6.1 과 별개 문제).

6.3 팀 번호 규약이 다르다

tracker 는 0 / 1 / -1(심판·골키퍼 등) / 빈칸(공)을 쓴다. 기여도 코드는 팀이 정확히 2개여야 하고, 심판으로 인식하는 키워드는 ref, 심판, none, nan, unknown 이다. -1 은 이 목록에 없으므로 세 번째 팀으로 세어지고, 다음에서 멈춘다.

팀이 2개여야 하는데 ['0', '1', '-1'] 이다. team 열을 정리할 것.

해결: tracker 쪽 drop_non_team 을 켜거나, 변환 단계에서 -1 행을 빼면 된다. 다만 골키퍼가 -1 로 묶여 있다면 함께 빠진다는 점에 주의해야 한다 — 골키퍼가 빠지면 골문 앞 공간을 센터백이 대신 받아 SC 가 부풀려진다. 축구 전용 모델을 쓰면 골키퍼가 별도 클래스로 나오므로, 골키퍼는 남기고 심판만 빼는 처리가 필요하다.

6.5 interpolated 열이 무시된다 경미

이것은 수식의 문제가 아니다 SC · PR · PA 자체는 정상 작동했다(효율성 공리 검산도 통과했다). 무너진 것은 "같은 선수"라는 개념이다. 그래서 프레임 단위 결과(SC/PR/PA 분포)까지는 의미가 있어도 선수 순위는 의미가 없다. 기여도 코드도 이것을 알고 경고를 출력한다 — "조각난 ID 로는 '선수별' 표가 선수를 가리키지 않는다."

증상 ② — TC 가 대부분 비어 있다(NaN)

두 가지가 겹쳤다.

  1. 구조적 이유 — 표를 보면 Red 쪽에는 SC·PR 은 있는데 PA 가 없고, Blue 쪽에는 PA 만 있고 SC·PR 이 거의 없다. 관측 구간 내내 Blue 가 공을 갖고 Red 가 수비했다는 뜻이다. TC 는 세 지표가 다 있어야 계산되므로 양쪽 다 낼 수가 없다. 더 긴 구간, 공수가 오가는 구간이 필요하다.
  2. 파편화 이유 — 1~2프레임만 존재하는 조각은 셋 중 하나만 걸리기 쉽다. 160행 중 대부분이 frames=1 이다.

증상 ③ — PR 이 거의 전부 0.0000 이다

PR 은 압박권 10m 밖에서는 정확히 0 이 된다(5.5 참고). 즉 수비수 중 누구도 볼 소유자의 10m 안에 없었다는 뜻이다. 진단 출력에도 그렇게 찍혀 있었다.

PR  압박권(d<=10m) 안  0.0% / 공까지 거리 중앙값 50.1 m

공까지 거리 중앙값이 50m 라는 것은 축구 경기에서 나올 수 없는 값이다. 이것은 압박을 안 했다는 뜻이 아니라 좌표계가 틀렸다는 신호다 — 6.1 의 픽셀/미터 문제이거나, 공 좌표와 선수 좌표의 정합이 깨진 경우다.

8 장고치는 순서

네 가지를 이 순서로 해야 한다. 순서가 중요하다 — 앞의 것을 안 고치고 뒤의 것을 고치면 헛수고가 된다.

1순위 · 픽셀 → 미터 변환 (호모그래피)

이것 없이는 나머지가 전부 무의미하다. 방법은 경기장의 알려진 지점 4개 이상을 화면에서 찍어 두 평면 사이의 변환 행렬을 구하는 것이다.

import cv2, numpy as np
# 화면에서 찍은 점 (픽셀)            실제 경기장 위치 (미터)
src = np.float32([[412, 880], [1503, 872], [1740, 402], [188, 410]])
dst = np.float32([[  0,  0], [ 105,   0], [ 105,  68], [  0,  68]])
H, _ = cv2.findHomography(src, dst)

pts = np.float32(df[["fx", "fy"]].values).reshape(-1, 1, 2)
xy  = cv2.perspectiveTransform(pts, H).reshape(-1, 2)
df["X"], df["Y"] = xy[:, 0], xy[:, 1]

쓸 만한 기준점: 경기장 네 모서리, 페널티박스 네 모서리, 골에어리어 모서리, 하프라인과 터치라인이 만나는 두 점, 센터서클 좌우 끝.

중계 영상이면 이것만으로 부족하다 위 방법은 카메라가 고정일 때만 한 번으로 끝난다. 중계 카메라는 패닝·줌·틸트를 하므로 프레임마다 변환 행렬이 달라진다. 이 경우 선택지는 셋이다.
  ① 고정 전술 카메라로 촬영한 영상을 쓴다 — 가장 쉽고 확실하다.
  ② 프레임마다 경기장 선을 검출해 변환을 다시 계산한다(허프 변환 등).
  ③ 경기장 키포인트를 직접 예측하는 모델을 붙인다(SoccerNet 계열 공개 모델이 있다).
①이 가능하다면 ①을 권한다. 기여도 계산은 어차피 경기장 전체가 보이는 좌표를 요구하는데, 중계 화면은 2/3 만 보여 주기 때문이다(7장의 usable 4% 참고).

손볼 것왜

track_buffer 를 60~90 으로가려진 선수를 더 오래 기억한다. 기본 30은 원본 프레임 기준이라 stride 3이면 실질 10프레임뿐이다.
bytetrack_recover_low 켜기낮은 신뢰도 검출을 트랙 잇기 용도로만 쓴다. 가려졌다 나온 선수의 ID 가 덜 끊긴다.

확인 방법: 20초 구간을 돌린 뒤 summary.json 의 unique_track_ids 를 본다. 22명 경기에서 이 값이 30 안쪽이면 성공, 100을 넘으면 아직 파편화 상태다. draw_boxes.py --labels id 로 영상을 만들어 번호가 얼마나 자주 바뀌는지 눈으로 보는 것이 가장 확실하다.

3순위 · 변환 스크립트 (tracks.csv → 기여도 입력)

6장의 나머지를 한 번에 처리하는 30줄짜리 스크립트다. 하는 일은 다섯 가지다.

  1. 공 행(track_id ≥ 1,000,000)을 따로 떼어 ball_x, ball_y 로 만든다
  2. 사람 행에서 심판(team = −1 이면서 골키퍼가 아닌 행)을 뺀다
  3. fx, fy 에 호모그래피를 적용해 X, Y(미터)를 만든다
  4. team 0/1 을 알아보기 쉬운 이름으로 바꾼다 (예: Home / Away)
  5. 골키퍼 track_id 목록을 뽑아 둔다 → 기여도 코드의 GK_IDS 에 직접 넣으면 자동 추정보다 정확하다

4순위 · 기여도 코드 쪽 정리

1~3을 해도 완벽한 추적은 없으므로, 남는 파편을 해석 단계에서 흡수하는 장치가 있으면 좋다.

  • 궤적 잇기(track stitching) — 시간이 겹치지 않으면서 끝점과 시작점이 시공간적으로 이어지는 조각들을 하나로 합친다. 끊긴 뒤 다시 나타난 선수를 되찾는 단계로, 지금 코드에는 없다.
  • 표 정리 — 관측이 너무 적은 조각은 표에서 빼고(엑셀에는 남기고), NaN 을 – 로 표시하고, 화면에는 22행 남짓만 보이게 한다.
  • TC 를 부분 지표로도 계산 — 세 지표가 다 없으면 지금은 NaN 인데, 있는 것끼리 가중치를 다시 나눠 계산하고 "무엇으로 계산했는지"를 함께 표시하면 짧은 클립에서도 쓸 수 있다.

용어뜻

IoU두 박스의 겹친 넓이 ÷ 합친 넓이. 1이면 완전히 같고 0이면 안 겹친다.

호모그래피한 평면(화면)의 점을 다른 평면(경기장)의 점으로 옮기는 3×3 변환 행렬. 기준점 4개면 구할 수 있다.
Shapley 값여럿이 협력해 만든 성과를 각자의 기여도에 따라 나누는 협력게임 이론의 배분 방식. 합이 보존되고(효율성), 같은 기여는 같은 몫을 받는다(대칭성).

AUC어떤 점수가 두 부류(패스를 받은 선수 / 안 받은 선수)를 얼마나 잘 가르는지를 0.5~1 로 나타낸 값. 0.5는 동전 던지기와 같고 1은 완벽하다.
순열검정정답을 무작위로 섞은 가짜 데이터에서도 같은 성능이 나오는지 확인하는 검정. "우연히 좋아 보이는 것"을 걸러낸다.
